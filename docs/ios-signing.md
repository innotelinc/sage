# iOS signing: what CI imports, and the certificate cap

Two certificates matter to a build, and only one of them is imported.

| Target | Signing | Certificate used |
| --- | --- | --- |
| `App` | Automatic, `-allowProvisioningUpdates` with the App Store Connect key | the distribution certificate from `IOS_DIST_P12` |
| `SageBroadcast` (extension) | **Automatic** — see the comment in `deploy/ios/add-broadcast-target.rb` | Xcode mints or reuses an Apple **Development** certificate |

The extension is the reason the account keeps filling up. An archive under automatic signing
resolves each target to *development* signing and only re-signs with distribution at export, so
every run needs an iOS App Development profile — and because a fresh runner has no private key
for an existing development certificate, Xcode asks Apple for one. The account has a hard cap on
Apple Development certificates, and the CI-created ones accumulate under the name
`Apple Development: Created via API`.

## The failure, and what it means

```
error: Choose a certificate to revoke. Your account has reached the maximum number of
certificates. To create a new one, you must choose a certificate to revoke.
  (in target 'SageBroadcast' from project 'App')
error: No profiles for 'us.inotell.sage.broadcast' were found: Xcode couldn't find any
  iOS App Development provisioning profiles matching 'us.inotell.sage.broadcast'.
error: No profiles for 'us.inotell.sage' were found: … 'us.inotell.sage'.
```

Read it as **account state, not code**: nothing in the repository changed between the last
successful build and this one, and the imported signing identity in both runs is the same
(`security find-identity` prints the distribution certificate in the throwaway keychain either
way). Build 64 failed here while build 63, hours earlier and from the same workflow, passed.

## The fix

```
gh workflow run asc-iap.yml -f certs=list
gh workflow run asc-iap.yml -f certs=purge-dev
```

`list` is read-only and prints each certificate, its type, its expiry and its serial — the count
is the thing to read. `purge-dev` deletes the `DEVELOPMENT` ones and **never touches
`IOS_DISTRIBUTION` or `DISTRIBUTION`**; the workflow then relists so the result is in the log.
Development certificates are regenerated by Xcode the next time a development build needs one,
which is why deleting them costs a machine nothing but a prompt.

Never revoke an `IOS_DISTRIBUTION` certificate to clear this: that is the one every TestFlight
build and every App Store submission signs with, and its replacement has to be reissued and its
`.p12` re-uploaded as a secret.

## How it is kept from coming back

The extension no longer needs a development certificate. The workflow asks the API for an App
Store profile per bundle id before the archive (`PROFILES=ensure` in `scripts/asc-iap.mjs`),
installs each `.mobileprovision` into the runner's profile directory, and exports the UUIDs as
`APP_PROFILE_UUID` and `EXT_PROFILE_UUID`. `add-broadcast-target.rb` then pins both Release
configurations to them:

```ruby
'CODE_SIGN_STYLE' => 'Manual',
'CODE_SIGN_IDENTITY' => 'iPhone Distribution',
'PROVISIONING_PROFILE_SPECIFIER' => profile,
```

Profiles are not capped, so this is repeatable; a local run without the UUIDs still falls back
to automatic signing. If a build ever fails at `Archive` with the text above again, the fallback
is still the same: `certs=list`, then `certs=purge-dev`, then rebuild.
