### To submit — three API writes, no workflow for this yet

The repository has no submission script for Mintmark (only `mobile/scripts/asc-compliance.mjs`
and the screenshot/archive jobs), so this is App Store Connect by hand or two API calls:

1. `PATCH /v1/appStoreVersions/d405a608-…` with
   `relationships.build = {type: 'builds', id: <build 13>}`.
2. `PATCH /v1/appStoreVersionLocalizations/<en-US>` with the What's New block above.
3. `POST /v1/reviewSubmissionItems` for the version, then
   `PATCH /v1/reviewSubmissions/<id>` with `submitted: true`.

After step 1 the version must be re-read: the attach is refused while a version holds
another build and Apple is still reconciling the new one, so a 409 there means retry,
not that build 13 is bad.

The empty draft `39c1d92d-b8fd-4026-83e4-3e7b8ea677d6` from 1.0 can be ignored;
`DELETE` on `reviewSubmissions` is refused (403) in every state and only the web UI
can remove it.

### Review notes (537)

```text
AthenIQ is a free companion app for AthenIQ Institute students. Signing in is optional: the catalog, course pages, lesson previews and credential verification work without an account. Sign in with a student account to enroll, download lessons for offline study, follow progress and collect certificates; registrars can sign in to see the payment queue. ```
```

**That last sentence is the risk.** Guideline 2.1 expects credentials for anything
behind a login, and "we will make one if you ask" is a common rejection — it costs a
review cycle, not just a message. Before submitting, create a student demo account
(enrolled, with progress and one certificate) and a registrar demo account, and put
both pairs in the notes. The app also gates a paid flow outside StoreKit ("paid for on
the web by transfer"): the notes already say so plainly, which is the right answer for
a reader app, but expect the reviewer to exercise it.

### Blockers, in order

1. ~~**Screenshots.**~~ **Cleared.** The app declares tablet support, so App Store
   Connect wants all three sizes before a version can go to review: 6.9-inch
   (1320×2868), 6.3-inch (1206×2622) and 13-inch iPad. Until today the draft only
   reported `screenshots: en-US APP_IPHONE_67` because the previous three capture runs
   were cancelled or failed **inside the Capture step** (44271497751 cancelled after
   ~1h03, 44264185404 failed after ~49m). Run 44285840658 cleared all three — it built
   Release, booted a 6.9-inch iPhone, a 13-inch iPad and a 6.3-inch iPhone, captured
   4 images per slot, and uploaded them. The read-back run 44296997741 reports
   `APP_IPHONE_67`, `APP_IPHONE_61` and `APP_IPAD_PRO_3GEN_129` each `4 complete, 0
   still processing, 0 failed` — "every known slot is on the draft". No re-run is
   needed; use the pair below only if Apple rejects an image later:

   ```
   gh workflow run ios-screenshots.yml -R innotelinc/atheniq -f upload=true
   gh workflow run ios-store-status.yml -R innotelinc/atheniq -f display=all
   ```

   The first captures on simulator hardware; the second re-reads the sets later, so
   `UPLOAD_COMPLETE` (still checking) can be told apart from a rejected image.

2. **App Privacy.** Publishing the questionnaire is a web-UI act and it is what a
   first submission dies on: `STATE_ERROR.APP_DATA_USAGES_REQUIRED` — "You must have
   published answers to your app's data usages". Saved is not published. Declare, for
   app functionality: contact info (the account email), user content (enrollments,
   progress), identifiers (user id), and the payment reference for transfer-paid
   courses; no tracking, no advertising. Build 3 collects none of it until a student
   signs in, which is what the notes say.

3. **Review contact.** The record carries `admissions@atheniq.institute`. App Review
   replies to that address and expects an answer within a day; if it is a shared or
   unmonitored inbox, point it at the address the other two apps use.

## 5 · Order of operations

1. **AthenIQ first**, because it is the only one that needs work that a rerun cannot
   fix: publish App Privacy and create the demo accounts. Its screenshot sets are now
   all three complete.
2. **Mintmark second**: attach build 13, write What's New, submit. Its screenshots and
   privacy are already in place, so it is the cheap one.
3. **Sage last**: nothing to change. Submit only after deciding the trial/consumable
   pricing still reads correctly in the purchase sheet — a build swap does not touch
   it, but it is what a reviewer will actually buy.

Two rules that cost a cycle each if forgotten:

- **Screenshots lock once a version is in review.** Editing them means cancelling the
  submission (`PATCH canceled: true`), which leaves the version `DEVELOPER_REJECTED`
  with its wells open — exactly the state Sage is in today — and then resubmitting.
- **An approved version never accepts new screenshots.** Once 1.1 for Mintmark is
  approved, any further art change rides a 1.2.
